The Envelope, as built

The contract the platform now runs on: one packet shape, four interceptors, a recorded lineage, a bus, and a decision that can be replayed.

CryptAlyst · architecture reference for the implemented system · commit b41fec2 · every number in this document was measured on the running platform, not estimated

1. What this document is

The design note The Envelope for CryptAlyst argued for the envelope and set out six phases of adoption. This document describes what was built, where it lives, and what it does when it runs. It is deliberately narrow: it covers the envelope and the pipeline around it, because that is the part of the platform that changed.

Three claims are made here, and each has evidence:

  • every publication passes the same four checks before its payload is computed;
  • a decision can be traced back to the packet it was made from, and replayed;
  • freshness is enforced from the packet's own computed_at, not a wall clock.
The invariant to protect. The packet shape never changes. Everything that varies — venues, indicators, models, stores — lives in the producers, interceptors and consumers around it. The moment a trading-specific field is added to the envelope, the design has failed.

2. The shape

Three parts, and nothing else. The data is the payload the operator computed. The meta is provenance: which plane, which topic, which key, which producer, at which generation, under which correlation id, computed when. The refs are the inputs it read — as references, so a tick batch stays in one place.

The pipeline record travels with the packet. A reader does not have to find a log line to learn which checks ran; the checks are in the envelope.

3. The pipeline

Every publication passes the same four interceptors, in this order, before the operator computes anything. That ordering is the point: a producer that may not write a topic never gets as far as spending compute on it.

stagequestionon failure
authoritymay this producer write this topic?refusal naming the producer and the topic
keyingis this topic keyed by a symbol?refusal naming the missing key
correlation—a cid is minted and chained to the parent
freshnessis computed_at within the topic's TTL?refusal quoting the age and the limit

A refusal is not a log line. It is an envelope on system.error carrying the stage, the rule and the number that tripped it — which is what makes "why not" something you can open.

4. The topic registry

One table declares every topic's plane, its permitted producers and its retention. A producer that is not listed is refused by the authority interceptor. Adding a topic is a row, not a code path.

planetopicsrecorded
marketprice · depth · candle · mini24h · ticksno — live only
intelsignal · flow · movers · board · ta · forecast · forecast.outcome · backtestyes
alertpumpdumpyes
modelsweep · selection · decision · fill · pnlyes
riskstate · refusalyes
control / systemcontrol.engine · system.erroryes

The market plane is deliberately not recorded: the bus is a state channel, not a job queue, and a price that is two seconds old is not worth storing as history.

5. Identity and lineage

Minting is local: a cid is created at the boundary that created the work, so work still starts when nothing central is reachable. What is central is the map — and here the map is a projection of the journal, rebuildable by replay.

A lineage read from the running journal

GET /api/envelope/chain?cid=del.decision-BTCUSDT-711…

lineage depth: 2
  model.decision   key=BTCUSDT  gen=1    parent=tel.forecast-BTCUSDT-…
  intel.forecast   key=BTCUSDT  gen=117  parent=–

The walk follows parent_cid backwards. The first implementation matched "cid equals this or parent equals this", which lists what came from a decision rather than what it was made of; a reviewer asking "why did we buy?" needs the inputs. That was found by testing the feature and fixed with a regression test.

6. The bus

The broker already carried one topic exchange per plane, so the envelope uses that topology rather than inventing a second one. Provenance is repeated as STOMP headers, so a consumer can filter without parsing the body.

Publishing is best-effort by design: if the broker is down the packet is still journalled and the request still answers. A bus outage stops a forecast being broadcast, not being computed.

Recorder statistics, measured

GET :8801/stats
  intel.forecast   184        market.candle   5 768
  market.price   12 454        market.depth  323 893
  rate         ~1 000 envelopes/s

That is the envelope path end to end: a producer publishes, the broker routes by plane, the recorder consumes and writes. Nothing on the hot path waits for the disk.

7. Freshness, enforced

The platform previously guessed staleness from a wall clock. Now the packet says when it was computed, the topic says how long an answer may live, and the refusal quotes both.

age = now − meta.computed_at        limit = topic TTL
age ≤ limit   → the verdict is allowed
age > limit   → REFUSED: "stale forecast", age 1 706 s, limit 60 s
Found by testing. Asking for a decision on the 4h frame returned a flat 1m forecast, because generations count per (topic, key) and both frames share a counter — "newest packet" meant "whichever was published last". The decision now filters on the packet's own interval and orders by computed_at. A regression test publishes a flat 1m and a falling 4h forecast and asserts the 4h decision uses the 4h one.

8. The orchestrator

Two inputs and no model knowledge: the capability table (derived from the topic registry — topic, producer, maximum age) and the journal (the newest packet per topic and key, with its generation and computed time). From those it decides serve or recompute.

GET /api/orchestrator/plan?symbol=BTCUSDT
  18 capabilities · 16 require recompute
  intel.forecast  gen 8  age 250 s  recompute  older than its deadline
  intel.signal    gen 0            recompute  nothing recorded

When it decides work is needed it publishes a control.engine packet naming the capability. It never calls a calculator directly: a request for work is an envelope like everything else, so it is recorded and can be replayed.

9. Backtest as replay

The weakest part of the old platform was that the backtest and the live system shared intent but not code. Here they share the code: replay reads the recorded forecasts, re-derives each verdict with the same rule the live path uses, and grades it against the price the market actually reached at anchor + horizon.

The scorecard, as it stands

metricvalue
packets replayed164

buy / sell / none0 / 7 / 157

This is the honest result. The platform declines to trade almost always, and the seven times it did, it was wrong. That is not a failure of the envelope — it is the envelope working. Before, the same models reported R² ≈ 0.97 and nobody could say whether that meant anything. Now the platform states what happened and keeps the packets that prove it.

11. What is not built yet

  • Producers for most intel topics. intel.signal, intel.flow, intel.ta and intel.board are registered but nothing publishes them, so the orchestrator correctly reports "nothing recorded" for each.
  • Fill and PnL packets. model.fill and model.pnl exist in the registry and nothing writes them; the trading trail stops at the decision.
  • A decision floor worth trading. The 0.05% threshold is why nothing trades. That is a strategy parameter, not an architecture one, and it has not been set.
  • The lake as a replay source. Replay currently reads the JSONL journal; the recorder's lake holds the same packets and is not yet a reader.
Where the code is. backend/internal/envelope/ — packet.go (shape), topics.go (registry), pipeline.go (interceptors), cid.go (identity), journal.go (recorder and replay), bus.go (RabbitMQ). The API surface is backend/internal/api/decision.go, replay.go, orchestrator.go and envelope_api.go.
